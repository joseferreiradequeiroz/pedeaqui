# PedeAqui Robustez Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Tornar o PedeAqui robusto contra concorrência, reenvios e falhas de dependências: locks, idempotência, Redis, outbox + RabbitMQ, gateway de pagamento fake com resiliência, saga com compensação, expiração e reconciliação.

**Architecture:** Monólito modular em Clean Architecture (.NET 8). A API grava pedido + outbox na mesma transação. Um novo host `PedeAqui.Worker` publica o outbox no RabbitMQ, consome os eventos e conduz o pagamento contra o `PedeAqui.PaymentGateway` (serviço fake separado), protegido por Polly. O Redis é a camada rápida (cache, rate limit, barreira de idempotência), com fallback. O PostgreSQL é a fonte da verdade.

**Tech Stack:** .NET 8, EF Core 8 + Npgsql, PostgreSQL 17, StackExchange.Redis, RabbitMQ.Client 7.x (sem MassTransit), Microsoft.Extensions.Http.Resilience / Polly 8, Serilog.AspNetCore, AspNetCore.HealthChecks.* 8.x, xUnit, Testcontainers 4.x (PostgreSql, Redis, RabbitMq), Scrutor (opcional).

**Spec:** `docs/superpowers/specs/2026-11-10-robustez-design.md` (leia antes de cada tarefa).

## Global Constraints

- **Nenhum comentário no código**, nem em produção nem em teste. Os nomes precisam explicar o código.
- **Não fazer `git commit`.** O dono faz commits atômicos depois. Ignore os passos de commit do template.
- Target `net8.0` em todos os projetos. Versões de pacotes compatíveis com net8 (EF Core 8.0.x, Npgsql EF 8.0.x).
- Seguir os padrões existentes: caso de uso = interface `IXxxUseCase` + classe `XxxUseCase` em `PedeAqui.Application/UseCases/<Área>/<Ação>/`, registrado em `PedeAqui.Application/DependencyInjectionExtension.cs`; repositórios divididos em ReadOnly/WriteOnly/UpdateOnly no Domain e implementados como `internal` na Infrastructure; exceções derivam de `PedeAquiException` com `GetStatusCode()`/`GetErrorMessages()`; mensagens de erro em `PedeAqui.Exception/ResourceErrorMessages.cs` (português).
- O Domain não referencia pacotes de infraestrutura. Os casos de uso não conhecem HTTP, Redis nem RabbitMQ.
- Todo valor numérico (TTL, tentativas, janelas, timeouts, limites) fica em `appsettings.json`, numa seção tipada com `IOptions<T>`.
- Testes de integração rodam em infraestrutura real via Testcontainers (Docker precisa estar de pé). O EF InMemory sai dos testes de integração. Os testes unitários continuam com os fakes em `tests/PedeAqui.UnitTests/Fakes`.
- Rodar a suíte inteira (`dotnet test PedeAqui.slnx`) ao final de cada tarefa. Ela precisa estar verde.
- Filas: RabbitMQ. Nada de AWS.

## Review Focus

1. **Cliente desconecta logo depois do commit de um `POST /api/orders` com `Idempotency-Key`.** A chave precisa terminar `Completed`, e o reenvio precisa receber o replay. A gravação do `Complete` usa `CancellationToken.None`. Teste na Task 9.
2. **Redis inalcançável desde o boot** (host errado, porta fechada). A API sobe, o catálogo responde do banco, o rate limit libera e a idempotência cai só no Postgres. Teste na Task 7.
3. **RabbitMQ fora do ar enquanto a API recebe pedidos.** O pedido é criado (201), a mensagem fica no outbox e é publicada quando o broker volta. Teste na Task 13.
4. **Gateway responde 4xx inesperado** (por exemplo, 400 de payload). Não pode haver retry; a mensagem vai para a DLQ e o pedido fica `AwaitingPayment` até o reconciliador. Teste na Task 14.
5. **`Idempotency-Key` inválida** (vazia, com mais de 100 caracteres ou só espaços). Responde 400 antes de qualquer gravação. Teste na Task 9.

**Interfaces:**

- `IIdempotencyLock.TryAcquire(string lockKey, TimeSpan ttl, CancellationToken)` → `Task<bool?>`: `true` = adquiriu (`SET NX PX`); `false` = ocupado; `null` = Redis indisponível. `Release(string lockKey)`.
- `IIdempotencyService.Begin(long userId, string key, string method, string path, string requestBody, CancellationToken)` → `Task<IdempotencyStart>`, com
  `abstract record IdempotencyStart { record Started(long RequestId); record Replay(int StatusCode, string? Body); record InProgressConflict; record PayloadMismatch; }`.
  Algoritmo: hash SHA-256 do JSON do corpo normalizado (re-serializado de forma canônica via `JsonNode`) → lock Redis `idem:{userId}:{key}` (`false` → `InProgressConflict`; `null` → segue) → busca no Postgres: não existe → insere `InProgress` e commita sozinho (23505 numa corrida → relê); existe com hash diferente → `PayloadMismatch`; `Completed` → `Replay`; `InProgress` com `LockedUntil > now` → `InProgressConflict`; `InProgress` vencido → retoma (atualiza `LockedUntil`) → `Started`.
- `Complete(long requestId, int statusCode, string? body, CancellationToken)` e `Release(long requestId, CancellationToken)` (apaga a linha). O filtro chama os dois com `CancellationToken.None`.
- Filtro: header `Idempotency-Key` obrigatório (1–100 chars, não só espaços) → senão 400. `Started` → executa a action; resultado 2xx/4xx → `Complete`; 5xx ou exceção não-`PedeAquiException` → `Release`; `PedeAquiException` 4xx → `Complete` com o ProblemDetails serializado. `Replay` → devolve o status e o corpo + header `Idempotent-Replayed: true`. `PayloadMismatch` → 422. `InProgressConflict` → 409.
- Opções: `Idempotency:KeyTtlHours=24`, `Idempotency:InProgressLockSeconds=60`.
- Limitação conhecida (para o README): entre o commit do negócio e o `Complete` existe uma janela; se o processo morrer ali, a retomada reexecuta. Não tentar resolver.

**Interfaces (contrato HTTP, usado pela Task 12):**
- `POST /payments`, header `Idempotency-Key` obrigatório, corpo `{ "orderReference": "string", "amount": 123.45 }` → 200 `{ "paymentId": "guid", "status": "Approved" | "Declined", "amount": 123.45 }`. Mesma chave + mesmo amount → mesmo resultado. Mesma chave + amount diferente → 422. Sem chave ou amount ≤ 0 → 400.

  1. Inbox já tem `(messageId, "payments")` → `Skipped`.
  2. Transação A: carrega o pedido. `IsFinal` → grava a inbox → `Skipped`. `Pending` → `StartPayment()`, `PaymentStartedAt=now`, commit. `AwaitingPayment` → segue (reentrega).
  3. `Charge("order-{id}", "order-{id}", order.Total)`. `PaymentGatewayUnavailableException` e `PaymentGatewayRejectedException` sobem para o consumidor.
  4. Transação B: relê o pedido; `Approved` → `ConfirmPayment()` → `Confirmed`; `Declined` → `FailPayment()` + `IOrderStockReleaser.Release(order, "Pagamento recusado do pedido #{id}")` → `Compensated`. Grava a inbox na mesma transação. Depois do commit, invalida o cache dos produtos.
  5. `ConflictException` no passo 2 (expirador ou cancelamento ganhou) → relê; se final → inbox → `Skipped`.
- Consumidor: `BasicQos(prefetchCount: RabbitMq:PrefetchCount=10)`, ack manual, um escopo de DI por mensagem, `LogContext` com `CorrelationId` e `MessageId`. Header `x-attempt` (int, começa em 0).
  - Sucesso/`Skipped` → `BasicAck`.
  - `PaymentGatewayUnavailableException` ou erro inesperado → se `attempt < 3`, publica a cópia na `payments.order-created.retry.{attempt+1}` com `x-attempt+1` e faz ack do original; senão `BasicNack(requeue:false)` → DLQ.
  - `PaymentGatewayRejectedException` ou payload inválido → `BasicNack(requeue:false)` direto (DLQ).
  - Shutdown: para de consumir, termina a mensagem em andamento (o token de stopping não cancela o processamento de uma mensagem já iniciada; usar um token próprio que só cancela depois do `ShutdownTimeout`).
